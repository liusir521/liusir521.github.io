AI Agent 工程体系详解：提示工程、上下文工程与编排工程

深入拆解 AI Agent 的三层工程体系：Prompt Engineering 设计智能、Context Engineering 管理记忆、Harness Engineering 编排执行

Apr 16, 2026
阅读时长: 7 分钟

引言

上一篇文章中，我们介绍了 AI Agent 的四个核心模块：范式、记忆、规划、工具。这些模块构成了 Agent 的"功能地图"，但要把它们真正工程化落地，需要从三个工程维度系统性地设计和优化。

业界逐渐形成共识：Agent 工程 = Prompt Engineering + Context Engineering + Harness Engineering。三者分别对应"大脑怎么思考"、“大脑记住什么”、“大脑如何行动”。

这三个概念最早由 Anthropic 的开发者关系团队在 2025 年公开提出，作为 Agent 系统设计的核心框架。本文将逐一拆解。

Prompt Engineering：让模型想对

Prompt Engineering 是最基础也是最先被关注的一层。它的目标是最大化模型在给定任务上的推理质量。

系统提示

系统提示是 Agent 的"宪法"——定义角色、约束行为边界、设定工作规范。

一个结构化的系统提示通常包含：

1
2
3
4
5

1. 角色定义：你是什么、能做什么
2. 行为约束：你不能做什么、什么情况拒绝
3. 输出规范：回复格式、风格、语言
4. 工具使用说明：何时调用工具、如何调用
5. 优先级规则：多目标冲突时的决策顺序

以 Claude Code 为例，它的系统提示实质上是多层次的指令集合：CLI 内置指令 + CLAUDE.md 项目指令 + Skills 领域指令。这种分层设计让 Agent 在不同场景下自动加载最相关的规则。

给 Agent 写指令和给人写需求文档有相通之处。经过大量工程实践验证的设计原则：

思维链

引导模型逐步推理，而非直接输出答案。这是最广泛验证的 Prompt 技术之一。

Zero-shot CoT：在 prompt 中加入"Let’s think step by step"，触发模型的分步推理能力。

Few-shot CoT：提供 2~3 个带推理过程的示例，让模型学会特定领域的推理模式：

Prompt Engineering 的局限

Prompt 不是万能的。它改变的是模型的"推理方式"，但改变不了模型的"知识边界"和"行动能力"。一个精心设计的 Prompt 无法让模型回答训练数据中不存在的事实，也无法让模型读写文件——这正是 Context Engineering 和 Harness Engineering 的用武之地。

Context Engineering：让模型记住

Context Engineering 管理什么信息在什么时候进入模型的注意力窗口。它是 Prompt Engineering 的自然延伸——Prompt 决定"怎么想"，Context 决定"基于什么想"。

上下文即资产

上下文窗口中的每一个 token 都是有限的资源。把上下文窗口看作一种"资产"需要管理：

资产概念 对应实践
预算 设定各类信息的 token 配额
投资回报 评估每类信息对输出质量的贡献
资产配置 动态调整信息类型占比
风险分散 不依赖单一信息源

组装的核心权衡：太少→缺乏信息→输出质量差；太多→噪声淹没关键信息→输出质量同样差。

上下文压缩

当对话积累到接近上下文窗口上限时，需要压缩。常用策略：

摘要压缩：让 LLM 将历史对话压缩为关键信息摘要。

1
2
3
4
5
6
7

原始对话（10轮，5000 token）
    ↓ LLM 摘要
"[摘要] 用户正在为 Go 项目添加 Redis 缓存功能。
已完成的步骤：1) 安装 go-redis 依赖 2) 定义 Cache 接口
3) 实现 RedisCache struct。当前问题：缓存过期策略选择，
讨论了 TTL、LRU、LFU 三种方案，倾向 TTL + 主动失效。
待确认：TTL 时长和缓存键命名规范。"

滑动窗口：保留最近 N 轮完整对话，超出部分用摘要替代。

分层压缩：

  • 第 1 层：最近 5 轮 → 完整保留
  • 第 2 层：5~20 轮 → 逐轮摘要
  • 第 3 层：20 轮以上 → 批量摘要

Claude Code 的 /compact 命令和自动压缩机制就是这三种策略的组合。

记忆系统设计

记忆是 Context Engineering 的核心子系统。三层记忆架构的实际工程考量：

短期记忆（会话内）：

1
2
3
4

设计要点：
- 大小上限：保持在上下文窗口 30%~50% 以内
- 淘汰策略：LRU（最近最少使用）或基于重要性评分
- 存储格式：[操作类型, 执行结果, 关键数据, 时间戳]

长期记忆（跨会话）：

1
2
3
4
5
6
7
8

存储流程：
用户偏好/经验 → Embedding 向量化 → 向量数据库 → 相似度检索

关键设计：
- 粒度：一条记忆一个独立事实，不要「一段话记所有事」
- 更新：检测到冲突时，以新代旧，而非追加
- 衰减：超时的记忆自动降低检索权重
- 去重：相似记忆合并，避免冗余污染检索结果

工作记忆（当前任务）：

工作记忆 = 当前对话上下文。不需要持久化，但需要高效管理。原则：信息越"热"越靠近上下文顶部，越"冷"越靠后或被压缩取代。

Harness Engineering：让模型能做

Harness Engineering 是最容易被忽视的一层，却是 Agent 从"对话机器人"进化为"行动系统"的关键。它负责工具调用、状态管理、错误恢复、并发控制等基础设施。

什么是 Harness

Harness 直译为"马具"或"线束"——把 LLM 这匹"野马"套上笼头，让它能干活。可以理解为 Agent 的运行时引擎。

它的核心职责：

│  工具调度    │  解析 tool_call，执行工具     │
│  状态管理    │  追踪任务状态，持久化进度     │
│  错误恢复    │  工具失败→重试/降级/报错     │
│  权限管控    │  危险操作拦截，用户确认       │
│  并发控制    │  并行调用管理，结果聚合       │
└──────────────────────────────────────────┘

def agent_loop(user_input, system_prompt, tools):
    context = assemble_context(system_prompt, user_input)
    
    while True:
        output = llm.invoke(context)
        
        if output.is_final_answer:
            return output.content
        
        if output.is_tool_call:
            result = execute_tool(output.tool_name, output.params)
            context.append({
                "role": "tool_result",
                "content": result
            })
            continue
        
        if output.is_error:
            context.append({
                "role": "system",
                "content": f"Error: {output.error}. Please adjust."
            })
            continue

关键设计点：

  • 循环终止条件：超时、最大轮次、LLM 输出结束标记
  • 工具调用格式化：遵循 function calling 协议（JSON Schema）
  • 结果注入位置：工具结果紧跟在调用指令之后，维持对话的因果链

工具粒度的权衡：

粗粒度（一个工具做很多事）：
  - 优点：LLM 调用次数少，延迟低
  - 缺点：灵活性差，工具描述复杂

细粒度（每个工具只做一件事）：
  - 优点：LLM 组合灵活，易于维护
  - 缺点：调用次数多，延迟高

实践：原子化工具 + LLM 组合调用。如 Read(读文件) + Edit(编辑文件)，
而非一个 ReadAndEdit 工具。

错误处理

工具执行不可靠——可能超时、返回异常、权限不足。Harness 需要应对：

def execute_with_retry(tool_call, max_retries=3):
    for attempt in range(max_retries):
        try:
            result = execute(tool_call)
            return result
        except TimeoutError:
            if attempt < max_retries - 1:
                wait_exponential_backoff(attempt)
            else:
                return error_result("Tool timed out after 3 retries")
        except PermissionError:
            # 权限错误不重试，直接返回
            return error_result("Permission denied")

LLM 驱动恢复：工具失败后，将错误信息返还 LLM，由 LLM 决定下一步。这是 Agent 区别于传统程序的核心特征——错误处理由"智能"驱动而非固定逻辑。

1
2
3
4

工具失败 → 简明的错误信息 → 注入上下文 → LLM 分析 → 
  ├── 重试（不同参数）
  ├── 换方案（另一个工具）
  └── 报告用户（无法自行解决）

并行与并发

无依赖的多个工具调用应该并发执行。这是 Harness 的关键优化点。

LLM 输出：[Read(file1), Read(file2), Grep(pattern, dir)]
              ↓                    ↓                    ↓
         并行执行             并行执行             并行执行
              ↓                    ↓                    ↓
         结果1                结果2                结果3

不需要复杂的锁机制——工具调用天然无副作用（只读）或独立（各自写不同文件）。Claude Code 的并行文件读取就是这个模式。

权限与安全

Harness 是 Agent 的安全闸门——在工具真正执行前做最终拦截：

1
2
3
4

LLM 决定调用工具 → Harness 检查权限 → 
  ├── 白名单匹配 → 直接执行
  ├── 需确认 → 用户确认 → 执行/取消
  └── 黑名单 → 拒绝执行

权限分级建议：

级别 操作类型 示例 策略
安全 只读操作 Read, Grep, Glob 自动放行
谨慎 本地写入 Write, Edit 首次确认后可放行
危险 命令执行 Bash, Exec 每次确认
禁止 破坏性操作 rm -rf, force push 硬阻止

Prompt Engineering  ████████░░  20% — 快速迭代，A/B 测试
Context Engineering ██████████████████░░ 50% — 持续优化，影响面大
Harness Engineering ████████████░  30% — 基础投入，稳定后变化少

Context Engineering 占比最高，因为它是三者中最快变化、最难做对的——每增加一个信息源、每更换一个场景，上下文组装策略都需要调整。

常见反模式

过度依赖 Prompt：试图用越来越长的 Prompt 解决所有问题，把模型当成唯一工程手段。结果是 prompt 臃肿、token 用量飙升、效果提升边际递减。

忽视 Context 质量：只关心"塞了什么"，不关心"塞得对不对"。检索到的文档不相关、记忆过时、压缩丢失关键信息，这些比 Prompt 写得差更致命。

Harness 过于简陋：工具描述模糊、错误处理缺位、没有重试机制。Agent 的"智商"被 Harness 拖累——不是 LLM 不知道怎么做，而是 Harness 没给它好的执行环境。

三层耦合过紧：Prompt 中硬编码了工具名、Context 组装逻辑嵌在 Harness 代码中。任何一层的改动都需要修改其他层，维护成本高。

工程建议

从 Prompt 开始，但不要止于 Prompt

搭建 Agent 的正确顺序：先用简单 Prompt 验证 LLM 能否理解任务 → 加入 Harness 赋予行动能力 → 用 Context Engineering 扩展知识边界。

这三步对应了 Agent 从"能对话"到"能行动"再到"能规模化"的演进路径。

上下文是最值得投资的部分

Prompt 写出 80 分的版本后，更多的优化收益来自 Context Engineering。一个信息准确、时效性好、噪声低的上下文，比一个精心雕琢的 Prompt 对输出质量的影响更大。

Harness 做得稳比快重要

工具调用的可靠性是 Agent 可用性的基础。宁可多花 1 秒做重试和校验，也不要让 Agent 在用户面前崩溃。

保持可观测性

在每层加入日志和指标：

  • Prompt：记录模板版本、token 用量
  • Context：记录检索命中率、压缩率、记忆使用量
  • Harness：记录工具调用成功率、延迟、重试次数

没有可观测性，三层优化都是盲调。

小结

维度 Prompt Engineering Context Engineering Harness Engineering
核心问题 怎么思考 基于什么思考 怎么行动
关键产物 系统提示、指令模板 记忆系统、上下文窗口 工具系统、事件循环
优化目标 推理质量 信息质量 执行可靠性
投入占比 ~20% ~50% ~30%
迭代速度 快（改文本即可） 中（需评测验证） 慢（改代码需测试）

Prompt Engineering 让 Agent 知道怎么做，Context Engineering 让 Agent 有足够信息判断，Harness Engineering 让 Agent 能把事做成。三层一起构成了从"输入-输出"的 LLM 到"感知-决策-行动"的 Agent 的完整工程路线图。
